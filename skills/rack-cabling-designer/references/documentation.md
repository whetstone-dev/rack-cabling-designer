# Documentation, as-built and change management

Use this to decide what to deliver, what `build` produces, how to version models, and how to plan work on live racks. Templates: `../assets/templates/site-survey.md` (requirements) and `../assets/templates/change-plan.md` (method of procedure).

## Deliverables and where they come from

| Deliverable | Purpose | Generated by |
|---|---|---|
| Rack elevations (front and rear) | Where everything is mounted, U by U | `elevation.html` |
| Cable schedule | Every cable, its ends, media, length, color, function, pathway, status, by channel | `cable-schedule.csv` (and in `README.md`) |
| Port maps | Which panel port goes where | Cable schedule filtered by device; `trace <model> <device>:<port>[:rear]` for one channel |
| Label sheet | Two labels per cable | `labels.csv` (see [labeling.md](labeling.md)) |
| Power budget | PDU capacity, normal and failover loads, heat per rack | `power.md` (see [power.md](power.md)) |
| Bill of materials | Equipment, PDUs, cords (rounded to stock lengths), bulk cable with slack, terminations, transceivers, power cords, blanking panels, labels | `bom.csv` |
| As-built / design README | Summary, findings, rack tables, power, schedule, BOM, assumptions and limits | `README.md` |
| Machine-readable results | Gate status, counts, all findings, channels | `report.json` |
| Test results | Copper certification, fiber OLTS/OTDR, PDU/circuit checks | **Not generated** — supplied by installers (OBSERVED) |

## What `build` does

`node "<skill-dir>/scripts/rackcab.ts" build <model> [-o dir] [--strict] [--allow-invalid]`

- Writes 7 files: `elevation.html`, `README.md`, `cable-schedule.csv`, `labels.csv`, `bom.csv`, `power.md`, `report.json`. Default folder: `<model-stem>-build` in the current working directory (e.g. `site.rack.json` → `site-build/`).
- Gate: any error blocks the build; `--strict` also blocks on warnings. `--allow-invalid` writes the files anyway as **drafts** and still exits 1 — say so when sharing them.
- Exit codes: 0 ok, 1 gate failed, 2 usage/input error, 3 internal error.
- BOM tuning: `policy.cableSlackPercent` (default 10% on installed links) and `policy.stockLengthsM` (default 0.5, 1, 1.5, 2, 3, 5, 7, 10, 15, 20, 30, 50 m cords; values from `scripts/lib/outputs/bom.ts`).
- Never edit generated files: change the model and rebuild.

## Design vs as-built vs change (`meta.status`)

| `meta.status` | README heading | Meaning |
|---|---|---|
| `design` (default) | Design documentation | Planned state, not yet installed |
| `as-built` | As-built documentation | Matches what is installed, verified on site (OBSERVED) |
| `change` | Change design | A planned change to an existing installation |

Item-level `status` on devices and cables: `planned`, `existing`, `remove`. In a change model, mark what stays as `existing`, what is added as `planned`, and what goes as `remove`. Removed cables are skipped by label rules and the BOM; removed devices are skipped by BOM and some power checks.

Caveats of the current toolkit when modeling changes:
- Devices marked `remove` still occupy their U, weight and power budget, so a same-U swap shows RCD-RACK-OVERLAP and the budget includes both old and new. Either keep "before" and "after" as two model revisions, or take the outgoing device out of the rack (drop `rack`/`position`) in the "after" model.
- Removed cables still appear in the schedule and `labels.csv` with status `remove`.
- There is no `diff` command: compare the before/after `cable-schedule.csv` (version control diff or spreadsheet compare) to build the change table.

## Revision control

- Keep `*.rack.json` in version control (git) with the generated build folder or with tagged releases of it.
- Bump `meta.revision` for every issued version (`A`, `B`, … for design; `1.0`, `1.1` for as-built is a common convention). Record `meta.author`.
- One model per site or room is easier to review than one huge model; keep ids stable across revisions.
- Record assumptions and catalog placeholders in `notes`; replace placeholders with datasheet values before procurement.
- After installation, update the model from the site walk (OBSERVED), set `meta.status: "as-built"`, rebuild, and archive.

## Change management on live racks

Every change to production cabling or power follows a written method of procedure (MOP), using `../assets/templates/change-plan.md`.

| Element | Content |
|---|---|
| Scope | Racks, devices, cables, circuits affected; model revision before → after |
| Risk and impact | Services on the touched ports; redundancy status; what happens if a step fails |
| Window | Maintenance window agreed with service owners; freeze periods respected |
| Pre-checks | Both PSUs healthy and on different feeds; redundant links up; no active alarms; backups/config saved; labels match model |
| Steps | One action per step, each with an expected result and a verification command or observation |
| Rollback | Exact reverse steps and the decision point/time limit for invoking them |
| Post-checks | Link state, error counters, optical power levels, PDU per-outlet load, monitoring green |
| Communication | Start/finish notices, escalation contacts |
| Sign-off | Implementer, reviewer, service owner |

Field rules: work on one side of a redundant pair at a time and verify it has recovered before touching the other; identify the cable at both ends (labels plus trace) before pulling; never remove a power cord before confirming the other PSU carries the load; keep removed cables out of the pathways.

## Handover checklist

- [ ] Model at `meta.status: "as-built"`, revision incremented, validated with no errors (state any accepted warnings).
- [ ] Build folder generated from that revision; `README.md` findings reviewed.
- [ ] Elevations checked against photos of each rack face.
- [ ] Every cable labeled at both ends; label numbers match the schedule.
- [ ] Copper certification and fiber test reports attached and linked to cable labels (OBSERVED).
- [ ] PDU feeds and circuit references verified on site with the electrician; per-outlet loads recorded where metered.
- [ ] Blanking panels installed on all open cold-face units; doors/side panels fitted.
- [ ] BOM reconciled with delivered material; spares listed.
- [ ] Open issues and INCONCLUSIVE items listed with owners.
- [ ] Sharing scope agreed (see below).

## Sharing caution

Generated documents reveal site names, room layout, rack positions, hostnames, circuit and panel references, and the redundancy design. Treat them as internal/confidential. Before sending outside the organization (vendors, contractors, public forums), confirm with the user and remove or generalize sensitive fields (`circuit`, `notes`, hostnames in `name`, `meta.site`). See [safety.md](safety.md).
